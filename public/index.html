One design decision

What the API does when you ask for 5000 records

Of the candidates — versioning from day one, or what the seed script taught me about data relationships — this is the one I would defend hardest, because it is the only one that changes what the server is willing to spend on your behalf.

The decision

Every list endpoint clamps limit to 100 instead of rejecting the request. Ask for 5000 records, get 200 with the first 100, and a meta.limit that quietly tells you what happened.

Why I made it

1. A 400 would punish a mistake the API can absorb for free. The caller asking for 5000 is almost never being malicious — they are a first-time integrator, or a script written against a different API, or someone who typed “give me everything” because they did not know there was a ceiling. Failing them teaches them nothing they can act on. Clamping still succeeds, and meta.limit means the next request is correct, so the caller self-corrects without ever being blocked.

2. On a shared, unauthenticated service, the query itself has to be the thing that cannot be abused. An unbounded ?limit=1000000 runs the same COUNT(*) plus a page-sized SELECT no matter who asks, and one such request can hold a connection from a pool of 10 hostage for everyone else. There are no accounts here, so the per-IP rate limiter is the only per-caller lever I have — which means the page size itself must be a constant the server controls. Clamping turns a caller-controlled variable into a known-safe one, so response time and database load stay predictable instead of being something a stranger can set.

3. It is the same rule everywhere else. offset must be a non-negative integer, and an unrecognised sort field is rejected outright with 400 INVALID_SORT and the allowed set listed. A malformed or hostile query parameter should never change the shape of the work the server does — it should only fail fast, or clamp to something already known to be safe. Clamping is the lenient half of that rule; the strict half is what the sort whitelist is for.

Capabilities

Built for integrators, not for a demo

The parts that usually get skipped, done properly — so nothing surprising happens on page 40 of a sync.

Offset and cursor paging

?limit&offset for jump-to-page, ?limit&cursor keyset paging for stable deep syncs. meta.nextCursor is handed back whenever there is more.

Real filtering and sorting

Typed filters per resource (city, mode, status, fare range, travel date) and whitelisted sort/order. An unknown sort field is a 400, never a silent default.

Write endpoints that validate

Create stops, routes, vehicles and bookings. Bodies are schema-checked, references are resolved server-side, and fares are computed from the route — not trusted from the client.

Honest errors

Typed codes such as INVALID_ID, CONFLICT, INVALID_REFERENCE and VALIDATION_ERROR with per-field details on 422.

Hardened page size

limit clamps to 100 instead of erroring, so a runaway ?limit=100000 costs the server nothing extra. Unbounded reads are impossible.

Rate limits that say so

100 requests per 60 seconds per IP on /api/v1/*, answered with 429 and a Retry-After header. /health sits outside the limiter on purpose.
